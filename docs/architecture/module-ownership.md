# 模块分工与边界

| 成员 | 负责模块 | 核心职责 |
| --- | --- | --- |
| 成员 1 | 身份、安全、后台与统计 | 账号认证、RBAC、用户资料与地址、设备/审计、管理后台基础框架、业务事件与指标口径、Git 管理 |
| 成员 2 | 商家与商家端 | 入驻、店铺、员工、客服及资质管理 |
| 成员 3 | 商品 | 类目、SPU、SKU、价格、库存、上下架、搜索、评价 |
| 成员 4 | 交易 | 购物车、结算、订单、支付、退款、状态机与并发安全 |
| 成员 5 | 聊天与消息 | 客服聊天、会话分配、消息中心与多渠道推送 |

## 成员 1 的接口边界

1. 统一身份中心负责登录、Token、角色、权限和数据范围判断；业务模块不得自行实现认证或信任客户端提交的主体 ID。
2. 商家身份、店铺关系及员工信息由商家模块维护；身份中心只保存账号、角色及授权关系。
3. 用户资料、地址、偏好及关注关系由用户模块维护；商家模块仅通过已定义接口访问必要的脱敏信息。
4. 管理后台的通用登录、路由守卫、菜单权限、审计与统计框架由成员 1 维护；系统管理员页面（用户与角色、系统日志）由成员 1 维护，平台管理员审核与运营页面由对应领域负责人实现。
5. 统计模块消费标准化业务事件，不直接修改订单、商品或聊天等领域表。

## 商家入驻跨模块边界

1. `merchant` 维护申请、资质文件、资质审核（通过即开通）、店铺及账号与店铺关系、撤销与重新授予。
2. 审核通过后的账号创建、密码哈希、`MERCHANT_OWNER` 授权和首次改密标记复用 `auth/security` 基础能力，不开放客户端自选角色。
3. SMTP 投递由 `message` 提供最小邮件服务；邮件失败不回滚审核事务，商家模块保存失败状态并允许平台官员重试。
4. 资质文件仅存入私有目录并通过 `merchant:qualification:audit` 鉴权接口下载，不配置静态文件映射。

## 跨模块约定

- 接口文档统一维护在 `docs/api/`。在 OpenAPI 组件接入前，`docs/api/auth.md` 是认证与 RBAC 的正式调用契约；各业务模块接入前必须阅读并使用 Bearer Token。
- 数据库迁移采用版本化脚本，所有表统一包含创建时间、更新时间及必要的版本号。
- 商家 ID、用户 ID、管理员 ID 从认证上下文获取，不接受客户端任意指定的数据范围。
- 高风险操作（权限变更、冻结、库存调整、退款审核等）必须写入审计日志。

## 前端目录边界

- 统一管理端按登录身份分离系统管理员与平台管理员；用户 Web 同时承载普通用户中心和商家工作台。
- 成员 2、3、4、5 分别只维护 `merchant`、`product`、`trade`、`message` 目录；项目管理员维护 `system`、`account` 和公共基础层。
- 已注册模块通过本模块 `index.ts` 贡献路由和菜单，不直接修改中央路由、布局或注册表。
- 公共认证、请求客户端、Token 刷新、路由守卫和错误处理由项目管理员维护；业务模块不得复制实现。
- 完整接入步骤和检查清单见 `docs/frontend-integration-guide.md`。

当前 `shop_follow` 仅为数据库预留：在 `merchant` 模块完成店铺实体、店铺状态和跨模块查询契约前，`user` 模块不得创建店铺关注接口或信任客户端提交的 `shopId`。
